Abstract

AIDCAT-AP aims to describe AI systems and AI agents so that they can be discovered and compared in catalogues. It builds on the machine learning models, datasets and infrastructure of MLDCAT-AP. Concepts coming from the AI Act, the Cloud and AI Development Act (CADA) and from agent descriptions such as A2A, MCP and OASF have been included, and a reference to them has been added for each class or property where needed, including those references to existing data models.

Introduction

AIDCAT-AP (AI DCAT-AP) is an Application Profile that extends MLDCAT-AP to describe AI systems and AI agents, together with their roles, interfaces, skills, capabilities and the software they use.

Status

This Application Profile has the status SEMIC Candidate Recommendation published at 2026-11-20.

Information about the process and the decisions involved in the creation of this specification can be consulted at the Changelog.

Terminology

An Application Profile is a data specification aimed to facilitate the data exchange in a well-defined application context. It re-uses concepts from one or more semantic data specifications, while adding more specificity, by identifying mandatory, recommended, and optional elements, addressing particular application needs, and providing recommendations for controlled vocabularies to be used. More information can be found on the SEMIC Style Guide.

Main Entities

The main entities are those that form the core of the Application Profile. The properties and their associated constraints that apply in the context of this profile are listed in a tabular form. Each row corresponds to one property. In addition to the constraints also cross-references are provided to DCAT. To save space, the following abbreviations are used to indicate in short the difference with DCAT:
  • A: reused as-is defined and expressed in DCAT [[vocab-dcat-3]]
  • E: reused with additional usage notes or additional restrictions compared to DCAT [[vocab-dcat-3]]
  • P: DCAT-AP profile specific extension where DCAT had no requirements earlier on specified
This reuse qualification assessment is with respect to a specific version of DCAT. Therefore it may vary over time when new versions of DCAT-AP are created.

AI Agent

Definition
An AI system or a coordinated set of AI systems that can perceive and act upon their environment, with a degree of autonomy, using tools as needed to achieve specific goals and adapt to changing inputs and contexts.
Reference
CADA
Usage Note
An AI agent is an AI system, so all properties of AI system apply. Use has interface for how the agent is invoked, uses service and uses software for what the agent calls, and has component for the AI systems that form the agent. The definition follows a proposal and may change.
Subclass of
AI System
Properties
For this entity the following properties are defined: goal , has capability , has component , has input modality , has interface , has native description , has output modality , has skill , uses service , uses software .
Property Range Card Definition Usage REF
goal Literal 0..* A specific goal that the AI agent is designed to achieve. May be omitted for general-purpose agents that have no single goal. The purpose of the system as a whole is given with intended use. No references available.
has capability Capability 0..* A capability that the AI agent supports. The AgentCapabilities of an A2A Agent Card map to this relation. The skills of the agent are described with has skill. Examples are streaming, push notifications and an extension of the A2A protocol. No references available.
has component AI System 0..* An AI system that is part of the coordinated set of AI systems forming the AI agent. No references available.
has input modality Modality 0..* The modality of the input that the AI agent can perceive. No references available.
has interface Agent Interface 0..* An interface through which the AI agent can be invoked. No references available.
has native description File 0..* A document in which the AI agent is described in its native format. An A2A Agent Card describes the agent and all of its interfaces, so it is linked once from the agent and not from every interface. The checksum of the file allows harvesters to detect changes of the card. An agent can have several native descriptions, for example an A2A Agent Card and an OASF record. No references available.
has output modality Modality 0..* The modality of the output that the AI agent can produce. No references available.
has skill Skill 0..* A skill that the AI agent offers. The skills of an A2A Agent Card map to this relation. No references available.
uses service Data Service 0..* A data service that the AI agent can call. Examples are the Data Service of an MCP server and a REST API. The interfaces through which the agent itself is invoked are described with has interface. No references available.
uses software Software 0..* Software that the AI agent executes or invokes to perform tasks. Examples are a command-line program, a script and an interpreter. Not to be confused with has software of the computer infrastructure, which lists the software installed on the infrastructure. No references available.

AI System

Definition
A machine-based system that is designed to operate with varying levels of autonomy and that may exhibit adaptiveness after deployment, and that, for explicit or implicit objectives, infers, from the input it receives, how to generate outputs such as predictions, content, recommendations, or decisions that can influence physical or virtual environments.
Reference
AI Act art_3.tit_1
Usage Note
The provider of an AI system and the provider of the machine learning model it uses can be different organisations.

Disclosure

Definition
A notification given to people that they are interacting with an AI system.
Reference
AI Act art_50 , Art. 50 GL
Usage Note
Declared by the provider for AI systems that interact directly with natural persons (AI Act, Article 50(1)). A system can have several disclosures, each with its own channel, wording and timing. Information that is only available in terms of use, URLs or documentation is not a disclosure in this sense. The labelling duties of deployers under Article 50(3) and (4) and the marking of outputs under Article 50(2) are not described by this class.
Properties
For this entity the following properties are defined: channel , notice , timing .
Property Range Card Definition Usage REF
channel Concept 1..* The form in which the disclosure is perceived by people. Possible values are text, audio and visual, as in the Commission guidelines on Article 50 (C/2026/6005, point 37). Give every channel that is used; a disclosure with several channels is multimodal. AI Act art_50 , Art. 50 GL
notice Literal 0..* The wording of the information as it is shown or spoken to people. Provide the text actually presented, with a language tag, and not a link to a document. Terms of use alone are not sufficient (Commission guidelines, point 38). The notice should be in a language the audience understands (guidelines, point 142). Omit only when the disclosure has no wording, for example a persistent icon (guidelines, point 37). AI Act art_50 , Art. 50 GL
timing Concept 0..1 The moment at which the information is given to people. Possible values are first interaction, periodic and on request. A system should have at least one disclosure given at the latest at the first interaction (AI Act, Article 50(5); Commission guidelines, points 40 and 143). Periodic and on request describe additional disclosures. AI Act art_50 , Art. 50 GL

Usage Guidelines

Support for implementation

The following section provides support for implementing the AIDCAT-AP.

JSON-LD context file

One common technical question is the format in which the data is being exchanged. For conformance with the AIDCAT-AP, it is not mandatory that this happens in an RDF serialisation, but the exchanged format SHOULD be unambiguously transformable into RDF. For the format JSON, a popular format to exchange data between systems, SEMIC provides a JSON-LD context file. JSON-LD is a W3C Recommendation [[[json-ld11]]] that provides a standard approach to interpret JSON structures as RDF. The provided JSON-LD context file can be used by implementers. This JSON-LD context is not normative, i.e. other JSON-LD contexts are allowed.

The JSON-LD context file is downloadable here.

Validation

To verify if the data is (technically) conformant to the AIDCAT-AP, the exchanged data can be validated using the provided SHACL shapes. SHACL is a W3C Recommendation to express constraints on an RDF knowledge graph.

To support the check whether or not a catalogue satisfies the expressed constraints in this Application Profile, the constraints in this specification are expressed using SHACL [[shacl]]. Each constraint in this specification that could be converted into a SHACL expression has been included. As such this collection of SHACL expressions can be used to build a validation check for data.

It is up to the implementers to define the validation they expect. Each implementation happens within a context, and that context is beyond the SHACL expressions here.

The shapes can be found here.

The Interoperability Test Bed (ITB) provides a SEMIC SHACL validation service where the linked shapes can be reused to validate data. The SHACL shapes for AIDCAT-AP are not yet available in the validator.

UML representation

The UML representation from which the AIDCAT-AP has been built is available here.

Governance

Versioning governance

All specifications produced in SEMIC will follow the versioning rule described by the SEMIC Style Guide rule PC-R3. In case a SEMIC asset is deprecated the asset will remain available through its PURI.

The serialisation will have:

  • a dct:isReplacedBy referencing the new assets used instead and
  • an adms:status indicating its deprecated status.

Governance requirements for re-used assets

In order to adhere to the SEMIC Style Guide rule GC-R2 a specification should have quality and governance standards for the assets that are being reused.

In order for an asset to be considered for reuse within a SEMIC specification it can be requested by a community member or it must adhere to the following requirements:

  • The asset is part of a recommendation by a major standards body or an EU institution.
  • The asset is actively being maintained.

After being taken into consideration the asset will be validated in three steps:

  • Syntax validation will be performed on the relevant artefacts.
  • Constraint validation will be performed on the relevant artefacts.
  • The PURI will be validated.
Once considered and validated an asset can be adopted if it is approved by the community.

Lexicalisation rules

In order to adhere to the SEMIC Style Guide rule SC-R3 a specification requires formal lexicalisation rules. The Style Guide proposes two options either by using RDFS or SKOS lexicalisation.

SEMIC uses and will use the RDFS lexicalisation for all of its specifications. More specifically:

  • rdfs:label is used to provide a human-readable version of a resource's name.
  • The usage of certain resource can be clarified in a skos:usageNote.

Quick Reference of Classes and Properties

This section provides a condensed tabular overview of the mentioned classes and properties in this specification. The properties are indicated as mandatory, recommended, optional and deprecated. These terms have the following meaning.
  • Mandatory property: a receiver MUST be able to process the information for that property; a sender MUST provide the information for that property.
  • Recommended property: a receiver MUST be able to process the information for that property; a sender SHOULD provide the information for that property if it is available.
  • Optional property: a receiver MUST be able to process the information for that property; a sender MAY provide the information for that property but is not obliged to do so.
  • Deprecated property: a receiver SHOULD be able to process information about instances of that property; a sender SHOULD NOT provide the information about instances of that property.
